# SovereignAI Edge — Full Project Issue Audit

**Date:** 21 August 2026  
**Scope:** Entire codebase — Backend (Python/FastAPI), Frontend (Next.js/React), Electron, Engine subsystems, Database, Security, Providers, Plugins, CLI  
**Method:** Static analysis with evidence from source code  
**Total Issues Found:** 57

---

## Executive Summary

SovereignAI Edge is a functional but unevenly matured project. The core inference path (FullRAM + LayerStream) works, but the project carries significant dead code, inconsistent patterns between the two database systems, missing test coverage on critical paths, and several concurrency/resource-management issues that could cause production failures under load.

**Overall Health:** Medium — functional for single-user desktop use (Electron/CLI), but production-grade reliability (multi-client, LAN deployment) requires fixes to the critical and high-severity issues identified below.

---

## Critical Findings

1. **`_load_model_locked()` unloads the active model before attempting to load the replacement** — if the new load fails, the user loses their model with no fallback.
2. **Silent stream failure** — engine exceptions mid-SSE stream leave the client with a truncated, unattributed response.
3. **Auth middleware queries SQLite on every HTTP request** — adds latency and DB load on every call.
4. **`trust_remote_code=True` hardcoded in 6 places** across LayerStream, TaskResolver, and Splitter — ignores `settings.trust_remote_code`.
5. ~~`LayerStreamEngine.generate()` doesn't strip prompt tokens~~ — FALSE POSITIVE (LayerStream builds output from scratch, prompt never included).

### [ISSUE-01] Unload-before-load loses active model on failure

**Severity:** Critical  
**Priority:** P0  
**Category:** Reliability  
**Status:** Confirmed  
**Location:** `backend/app/services/model_manager.py` — `_load_model_locked()`

**Problem:**  
`_load_model_locked()` calls `await self.unload_model()` unconditionally at line 150, before attempting to load the new model. If the new model fails to load (bad path, unsupported architecture, OOM), the previous model is already unloaded with no rollback.

**Evidence:**  
```python
async def _load_model_locked(self, model_id, mode, model):
    await self.unload_model()  # <-- unloads BEFORE attempting load
    # ... then tries to load new model
    try:
        await engine.load()
    except Exception:
        await engine.unload()  # cleans up the failed engine, but old is gone
        raise
```

**Impact:**  
User loses their active model with no recovery path. Must manually reload.

**Root Cause:**  
Sequential load-unload assumed load would always succeed.

**Recommended Fix:**  
Save the previous engine reference; restore on failure. Or only unload after successful load.

**Risk of Fix:**  
Low — just reordering operations.

**Validation:**  
Test: load model A, attempt load of nonexistent model B, verify model A is still active.

### [ISSUE-02] Silent stream failure mid-SSE

**Severity:** High  
**Priority:** P1  
**Category:** Reliability  
**Status:** Confirmed  
**Location:** `backend/app/api/chat.py` — `stream_response()`

**Impact:**

**Root Cause:**  
No error handling in the streaming loop.

**Recommended Fix:**  
Wrap the `async for` in try/except and yield an error event before returning.

**Risk of Fix:**  
Low.

**Validation:**

### [ISSUE-03] Auth middleware queries SQLite on every request

**Severity:** High  
**Priority:** P1  
**Category:** Performance  
**Status:** Confirmed  
**Location:** `backend/app/security/middleware.py` — `_security()`

**Problem:**  
`_security(request)` calls `svc.get_security()` which opens a new SQLite connection, queries the settings table, and closes it — on every HTTP request. This adds ~1-5ms per request.

**Evidence:**  
```python
def _security(request: Request) -> dict:

    if svc is None:
        return {}
    try:
        return svc.get_security() or {}  # <-- opens DB connection per call
    except Exception:
        return {}
```

**Impact:**  
Every API call pays 1-5ms for a DB roundtrip. On LAN with auth enabled, this is significant.

**Root Cause:**  
No caching of security settings.

**Recommended Fix:**  
Cache security settings in `app.state`, invalidate on settings update.

**Risk of Fix:**  
Low — add cache + invalidation on `update_security()`.

**Validation:**  
Profile request latency before/after.

### [ISSUE-04] `trust_remote_code=True` hardcoded in 6 places

**Severity:** High  
**Priority:** P1  
**Category:** Security  
**Status:** Confirmed  
**Location:**  
- `backend/app/engines/layerstream/executor.py:123,148,163,166`
- `backend/app/core/task_resolver.py:12,15`
- `backend/app/engines/layerstream/splitter.py:99`

**Problem:**  
LayerStream, TaskResolver, and WeightSplitter all hardcode `trust_remote_code=True`, ignoring `settings.trust_remote_code`. FullRAMEngine correctly uses the setting. This means untrusted model repos can execute arbitrary Python code through LayerStream even when the user has `trust_remote_code=False`.

**Evidence:**  
```python
# task_resolver.py
config = AutoConfig.from_pretrained(model_path, trust_remote_code=True, ...)

# layerstream/executor.py
tok_kwargs = {"trust_remote_code": True, "local_files_only": True}

# splitter.py
kwargs = {"trust_remote_code": True, ...}
```

**Impact:**  
Security bypass — arbitrary code execution from untrusted model repos.

**Root Cause:**  
LayerStream was written before the `trust_remote_code` setting was added.

**Recommended Fix:**  
Replace all `trust_remote_code=True` with `settings.trust_remote_code`.

**Risk of Fix:**  
Some models may require `trust_remote_code=True`. Users can set the setting to enable it.

**Validation:**  
Load a model with `trust_remote_code=False`, verify it loads without executing remote code.

**Severity:** N/A  
**Priority:** N/A  
**Category:** Correctness  
**Status:** FALSE POSITIVE

```python
output_ids = output_ids[prompt_tokens:]  # must strip prompt
```

**Resolution:**  
Removed dead `prompt_tokens` variable, added clarifying comment. No functional change needed.

### [ISSUE-09] WebSocket metrics spawns `nvidia-smi` subprocess per-client per-second

**Severity:** Medium  
**Priority:** P2  
**Category:** Performance  
**Status:** Confirmed  
**Location:** `backend/app/websocket/metrics.py:55-64`

**Problem:**  
Each connected WebSocket client runs `subprocess.run(["nvidia-smi", ...])` every 1 second. With N clients, that's N `nvidia-smi` processes per second. `nvidia-smi` takes 50-200ms and is expensive.

**Evidence:**  
```python
while True:
    cpu = psutil.cpu_percent(interval=0.1)
    await asyncio.sleep(0.9)
    ...
    res = subprocess.run(["nvidia-smi", ...], timeout=0.5)
```

**Impact:**  
With 5+ WebSocket clients, GPU monitoring becomes a bottleneck. On systems without NVIDIA GPU, the subprocess silently fails (good) but still spawns and waits for timeout.

**Root Cause:**  
No shared caching of GPU metrics.

**Recommended Fix:**  
Cache GPU metrics in a background task; share across all clients.

**Risk of Fix:**  
Low — add a single background task that updates GPU stats every 1s.

**Validation:**  
Connect 5 WebSocket clients, verify `nvidia-smi` is only called once per second.
